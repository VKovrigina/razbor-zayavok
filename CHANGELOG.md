- **Новые этапы CRM + примечание с ТЗ (2026-07-23):** воронка Partners расширена — «Первичные

- **Цепочка напоминаний доработана + этап «Молчание» (2026-07-23):** `process_scheduler_tick`
  теперь (1) перечитывает сделку из БД после лока и не шлёт напоминание, если ответ клиента уже

  `AMOCRM_STAGE_SILENCE_ID=82845866`, этап уже существовал в amoCRM). Та же цепочка теперь

- **FAQ включён, реальный контент для 3 пунктов (2026-07-23):** `FAQ_ENABLED = True`.

### Fixed
- **P-016 (2026-07-28):** подготовка первого сообщения (`checklist.assess`/`assess_topic` +
  `templates.first_message` в `core/state_machine.py: process_new_deal`) не была защищена от
  сбоя — исключение ДО попытки отправки (уже реализовалось как P-036) оставляло сделку в `NEW`
  навсегда: ни поллер (`deal_exists`), ни шедулер (статус вне `AWAITING_STATUSES`) её больше не
  подхватывали. Теперь эта подготовка обёрнута в try/except: сбой сразу помечает сделку `FAILED`
  (`repo.mark_failed`) и заводит задачу Варваре (`TASK_TEXT_PREP_FAILED`) — сообщение клиенту при
  этом гарантированно не отправлено. Сбой ПОСЛЕ реальной отправки намеренно не покрыт этим фиксом
  (нельзя маркировать `FAILED` сделку, которой сообщение уже ушло) — остаётся риском P-038.
- **P-019 (2026-07-28):** FAQ-ветка `handle_incoming_reply` вызывала `repo.restart_reminder_cycle`
  безусловно, даже если отправка автоответа клиенту падала — бот считал, что цикл ожидания
  продолжается, а клиент не получал ничего. Теперь `restart_reminder_cycle`/задача Варваре
  выполняются только при подтверждённой успешной отправке; провал отправки трактуется как «ответа
  в базе знаний нет» — обычная эскалация с `REPLY_AMBIGUOUS`.
- **P-036 (2026-07-27, найдено на проде):** после подключения реального `ANTHROPIC_API_KEY`
  LLM-ветка `core/checklist.py: assess_topic` первый раз в проде реально выполнилась — и упала с
  `KeyError: 'topic'`. Причина: в схеме tool-вызова поле `topic` идёт ПОСЛЕ длинного
  `per_criterion_analysis`, и при `max_tokens=300` ответ модели для тем с 5 критериями
  (`tilda_iiko`) обрезался раньше, чем модель успевала дописать `topic`. Необработанное исключение
  вылетало из `process_new_deal` через `amo/poller.py: poll_once` (без try/except вокруг лида) —
  ровно сценарий из аудиторской находки `P-016`. Две реальные сделки (39683277 — Анастасия
  Шильмейстер, 39683965 — Улжан) навсегда зависли в статусе `NEW` без единого сообщения клиенту и
  без задачи Варваре. Исправлено: `max_tokens=1024`; `assess_topic`/`assess_case` теперь читают
  поля инструмента через `.get(...)` с безопасным дефолтом («тема не распознана» /
  «описания недостаточно») вместо `[...]`, поэтому обрезанный/некорректный ответ модели больше не
  роняет обработку. Обе зависшие сделки вручную дообработаны через `state_machine.process_new_deal`
  на исправленном коде — первые сообщения в Telegram отправлены. ⚠️ Общий риск P-016 (чек-лист/
  шаблоны не защищены try/except в `process_new_deal`) остаётся открытым для других потенциальных
  сбоев — не закрыт этим фиксом.
- **P-035 (2026-07-24, найдено на проде):** сразу после запуска с реальной email-интеграцией
  бот ошибочно «склеил» две НЕсвязанные сделки (разные email, разные клиенты) в одну, потому что
  у обеих в поле Telegram в CRM стояла заглушка `-` (не заполнено) — код считал её настоящим
  username и совпадением идентификаторов. Сделка-жертва (39653787) была неверно переведена в
  `BLOCKED`. `amo/actions.py: _clean_username` теперь проверяет, что значение похоже на реальный
  Telegram-username (5-32 символа, буквы/цифры/подчёркивание, начинается с буквы) — иначе
  возвращает `None`, как для по-настоящему пустого поля. Пострадавшая сделка вручную восстановлена
  (`amo_actions.move_to_negotiations` + примечание в CRM + `repo.set_awaiting_first_sent`).
- **P-009 (2026-07-24):** `handle_incoming_reply` больше не бросает входящее сообщение клиента
  мгновенно, если сделка занята (напр. шедулер шлёт напоминание) — теперь пробует получить
  блокировку ещё 4 раза с паузой 15с (~60с суммарно), и только если не вышло — логирует
  предупреждение с текстом потерянного сообщения.
- **P-010 (2026-07-24):** конфликт идентификатора клиента (новая заявка от того же Telegram/email,
  пока старая сделка ещё активна) больше не заканчивается тем, что НОВАЯ сделка молча помечается
  `FAILED`, оставляя старую в базе висеть с риском её случайно найти при поиске по email/telegram
  (см. `get_deal_by_email`/`get_deal_by_telegram_peer`). Теперь наоборот: СТАРАЯ сделка
  автоматически переводится на этап «Блок» и получает новый локальный статус `BLOCKED` (в отличие
  от `CLOSED_NO_REPLY`, окончательно, без переоткрытия), Варваре ставится задача с упоминанием id
  новой сделки, а бот продолжает работу только с новой сделкой по обычному сценарию. Работает
  одинаково для Telegram- и email-сделок. Новая функция `db/repository.py: block_superseded`;
  `TERMINAL_ESCALATED_STATUSES` + `FAILED` объединены в `db/models.py: INACTIVE_STATUSES`
  (используется и в `find_conflicting_active_deal`, и в `handle_incoming_reply`).
- **P-011 (2026-07-24):** `_send_first_contact` теперь ловит ЛЮБУЮ ошибку при отправке в Telegram
  (`except Exception`), а не только известные `TelegramSendError`-обёрнутые случаи (FloodWait/
  PeerFlood/приватность/неверный username) — незнакомые ошибки Telethon (забаненный аккаунт,
  сетевой сбой) теперь тоже дают шанс на email-резерв вместо того, чтобы сделка терялась молча,
  минуя даже финальный `mark_failed`+задачу Варваре.
- **P-007 (2026-07-24):** `db/repository.py: create_deal_new` теперь ставит флаг канала сделки
  сразу при создании (Telegram, если в CRM есть username, иначе email) — до какой-либо попытки
  отправки. `email_channel/poller.py` перед обработкой входящего письма проверяет этот флаг: если
  канал сделки — Telegram, письмо не запускает классификацию/эскалацию, а просто добавляется в
  сделку примечанием `Почта: {текст письма}`. Закрывает гонку, при которой письмо, пришедшее пока
  бот ждёт антибан-паузу перед первой Telegram-отправкой, могло эскалировать сделку по email-ветке
  параллельно с Telegram-веткой и быть перезаписано ею (или наоборот).
- **P-008 (2026-07-24):** в `handle_incoming_reply` порядок изменён — `repo.escalate(...)`
  (с несколькими попытками при сбое, `_escalate_with_retries`) теперь вызывается ПЕРВЫМ, до
  примечания с ТЗ/ответа клиенту/смены этапа CRM/задачи Варваре, а не последним. Если
  зафиксировать эскалацию так и не удалось — ничего из побочных эффектов ещё не произошло,
  сделка просто разблокируется для повторной попытки без риска задвоить ответ/задачу/примечание.

## Convention

- **Added** — новая функциональность
- **Changed** — изменения существующей функциональности
- **Deprecated** — функциональность будет удалена
- **Removed** — функциональность удалена
- **Fixed** — багфиксы
- **Security** — security фиксы

Каждая запись = ссылка на PR + краткое описание для пользователя (не для разработчика).
