# ИИ-агент amoCRM ↔ Telegram/Email (партнёрский отдел Альбато)

Реализация сценария из [`Логика ИИ агента.md`](./Логика%20ИИ%20агента.md): когда сделка в amoCRM
(воронка Partners) попадает на этап «Новый контакт», агент пишет клиенту в Telegram от личного
аккаунта Варвары, классифицирует ответ (Claude), ставит задачи в amoCRM и ведёт напоминания при
отсутствии ответа. Email — fallback-канал.

## 1. Установка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Дальше заполните `.env` — см. разделы ниже.

## 2. Telegram (личный аккаунт, обязательно)

1. Зайдите на https://my.telegram.org, авторизуйтесь номером телефона аккаунта Варвары.
2. Создайте приложение (App title/Short name — любые) → получите `api_id` и `api_hash`.
3. Заполните в `.env`: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_PHONE` (в формате `+7...`).
4. При первом запуске `python main.py` в консоли попросит код из Telegram (и пароль 2FA, если он
   включён) — это происходит один раз, дальше сессия сохраняется в файл
   `TELEGRAM_SESSION_PATH` (по умолчанию `data/telegram.session`). **Не удаляйте и не коммитьте
   этот файл** — потеря сессии означает повторный вход.

## 3. amoCRM

Нужны права на чтение сделок/контактов и создание задач/изменение сделок.

**Вариант А (проще): долгосрочный токен.** В amoCRM: Настройки → Интеграции → создайте
приватную интеграцию → сгенерируйте долгосрочный токен (живёт ~год). Впишите его в
`AMOCRM_ACCESS_TOKEN`, остальные OAuth-поля (`AMOCRM_CLIENT_ID` и т.д.) можно оставить пустыми.

**Вариант Б: полноценный OAuth (client_id/secret/refresh_token).** Если интеграция настроена
через OAuth-приложение amoCRM — заполните `AMOCRM_CLIENT_ID`, `AMOCRM_CLIENT_SECRET`,
`AMOCRM_REDIRECT_URI`, а также `AMOCRM_REFRESH_TOKEN`, полученный после первого обмена
авторизационного кода (это разовая ручная процедура по документации amoCRM, вне рамок этого
скрипта). Сервис сам обновит `access_token` перед истечением.

**ID воронки/этапов/полей.** Через API (замените `{token}` и `{domain}`):

```bash
curl -H "Authorization: Bearer {token}" https://{domain}.amocrm.ru/api/v4/leads/pipelines
curl -H "Authorization: Bearer {token}" https://{domain}.amocrm.ru/api/v4/leads/custom_fields
```

Найдите в ответе воронку **Partners** и её этапы «Новый контакт» / «Первичные переговоры» /
«Блок» → впишите их числовые `id` в `AMOCRM_PIPELINE_ID` / `AMOCRM_STAGE_NEW_CONTACT_ID` /
`AMOCRM_STAGE_NEGOTIATIONS_ID` / `AMOCRM_STAGE_BLOCKED_ID`. Аналогично найдите поля сделки
«Telegram», «Стек сервисов», «Кейс» → их `id` в `AMOCRM_FIELD_ID_*`.

**ID пользователя Варвары** — `GET /api/v4/users`, найдите нужного пользователя → впишите его
`id` в `AMOCRM_VARVARA_USER_ID`.

## 4. Anthropic

Впишите `ANTHROPIC_API_KEY` в `.env`. Модель по умолчанию — `claude-haiku-4-5-20251001`
(дешёвая и достаточная для классификации трёх категорий); при необходимости замените в
`ANTHROPIC_MODEL`.

## 5. Email fallback (не обязателен для первого теста, но нужен для полного сценария)

Заполните `EMAIL_FROM_ADDRESS`, `EMAIL_SUBJECT`, SMTP- и IMAP-доступы почтового ящика, от
которого будут уходить письма клиентам и на который будут приходить их ответы. Если
`EMAIL_IMAP_HOST` не заполнен — сервис запустится, но не будет проверять входящие письма
(в лог попадёт предупреждение).

## 6. Запуск

```bash
python main.py
```

При старте сервис проверит обязательные переменные окружения (упадёт с понятной ошибкой, если
что-то не заполнено), поднимет Telegram-клиент, и запустит в фоне: поллинг amoCRM (раз в
`AMOCRM_POLL_INTERVAL_SECONDS`, по умолчанию 90 сек), шедулер напоминаний (раз в
`SCHEDULER_TICK_SECONDS`, по умолчанию 60 сек) и, если настроен email, поллинг почты.

Второй процесс — `python main_cases.py` (выдача кейсов партнёрам), запускается отдельно.

## 6а. Сервер (systemd)

Оба процесса — отдельные systemd-службы: `deploy/razbor-main.service` и
`deploy/razbor-cases.service`. `Restart=always` поднимает процесс после любого падения, а
встроенный сторож (`reporting/watchdog.py`) сам завершает зависший процесс — если цикл молчит
дольше 20 минут или Telegram 3 проверки подряд не отвечает — с алертом в вебхук.

**Переезд — строго в таком порядке:**
1. Остановить агента на старой машине (оба процесса) и убедиться, что не запущен
   (`ps aux | grep main`). Две копии на разных машинах = одна Telegram-сессия с двух мест:
   Telegram может сбросить авторизацию, клиенты получат двойные сообщения. Блокировка
   `data/*.lock` ловит второй запуск только на ОДНОЙ машине.
2. Скопировать на сервер код, `.env` и всю папку `data/` (базы `app.db`, `app_cases.db`,
   файлы `telegram.session`, `telegram_cases.session` — повторная авторизация не понадобится).
3. `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt` (версии закреплены).
4. В обоих `.service` заменить `AGENT_USER` и `/opt/razbor-zayavok`, скопировать в
   `/etc/systemd/system/`, затем:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now razbor-main razbor-cases
   journalctl -u razbor-main -f      # лог main.py
   journalctl -u razbor-cases -f     # лог main_cases.py
   ```
   Объём логов ограничивает journald: в `/etc/systemd/journald.conf` задать, например,
   `SystemMaxUse=200M` (и `sudo systemctl restart systemd-journald`). Шумные INFO-логи telethon
   и httpx в коде приглушены до WARNING.
5. Остановка/перезапуск — только `sudo systemctl stop|restart razbor-main` (SIGTERM = штатная
   остановка, без ложного алерта о краше).

## 7. Проверка сценария

1. Создайте тестовую сделку в воронке Partners на этапе «Новый контакт», с заполненным полем
   Telegram (username второго тестового Telegram-аккаунта, которым вы можете отправить ответ) и
   полями «Стек сервисов»/«Кейс». В течение ~1–2 мин должно прийти первое сообщение.
2. Ответьте с тестового аккаунта: явным согласием / словом «неактуально» / уточняющим вопросом —
   на трёх разных тестовых сделках. В каждом случае: сделка должна уйти на этап «Первичные
   переговоры», должен прийти соответствующий ответ бота, в amoCRM должна появиться задача на
   Варвару. Повторное сообщение в этот же чат бот больше не должен обрабатывать.
3. Чтобы проверить цепочку напоминаний без ожидания реальных суток — откройте
   `data/app.db` (любым sqlite-клиентом) и вручную поставьте `next_action_at` тестовой сделки в
   прошлое; в течение следующего тика шедулера должно прийти соответствующее сообщение.
4. Чтобы проверить email-fallback — создайте сделку без заполненного поля Telegram, но с email
   на привязанном контакте: сообщение должно уйти письмом.

## Структура проекта

См. раздел "Структура проекта" в плане реализации / комментарии в начале каждого модуля —
`core/state_machine.py` содержит всю бизнес-логику переходов состояний и не зависит от того,
через какой канал (Telegram/email) отправляется сообщение.

## Известные ограничения этой итерации

- Работает как один локальный процесс (без вебхуков, без публичного сервера) — амоCRM опрашивается
  поллингом. При переезде на VPS вебхуки станут разумным upgrade, но не обязательны.
- Один активный отслеживаемый диалог на клиента (username/email) — если у контакта уже есть
  необработанная сделка, вторая помечается как конфликт и уходит в ручную задачу на Варвару.
- Массовая переписка с личного Telegram-аккаунта нарушает пользовательское соглашение Telegram —
  в коде заложены базовые анти-бан меры (задержки, дневной лимит, обработка FloodWait/PeerFlood),
  но риск ограничений полностью не исключён.
